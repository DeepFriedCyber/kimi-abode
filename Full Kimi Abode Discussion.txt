Great clarifications — these three points actually change the design in important ways. Taking each in turn:
1. Bulletproof NL search: don't harden the LLM, build a degradation chain

The key reframe: bulletproof search doesn't come from making the LLM infallible (impossible) — it comes from a chain where each tier is simpler and more reliable than the last, plus UX that makes even a wrong parse recoverable.

The failover chain:
Tier 	Component 	Latency 	Dependency 	Role
0 	Deterministic parser (high confidence) 	~5ms 	None 	~70–80% of queries
1 	LLM parse — primary provider 	~600ms 	Anthropic 	Complex long-tail
2 	LLM parse — second provider 	~600ms 	OpenAI/Groq 	Provider outage
3 	Semantic parse cache 	~20ms 	Redis 	Repeat/similar queries
4 	Deterministic parser (forced) 	~5ms 	None 	Total LLM outage
5 	Raw Postgres full-text 	~30ms 	Postgres only 	Last resort

Why the deterministic parser is your real bulletproofing: property queries are extremely formulaic — beds, price ceiling, location, type, features, "near schools/station." A regex + UK gazetteer + synonym-map parser handles the large majority of real queries with zero external dependencies. It runs in-process, can't go down, and can't be prompt-injected.

A design upgrade this enables: run the deterministic parser first with a confidence score. High confidence → skip the LLM entirely (faster and free — this strengthens your 95% cost story). Low confidence → LLM. In an outage, the same parser becomes the fallback. One component serving both resilience and cost.

Three non-obvious requirements:

    The embedding failover trap: if your embedding API dies, a fallback embedding model produces vectors in an incompatible space — you can't mix them in pgvector. Fix: dual-embed every property at ingestion (primary 1536d + a self-hosted bge model as backup, stored as halfvec, ~3.5GB per 1M listings). Or accept keyword-only degraded mode. Decide now, not during an outage.
    Editable parsed filters in the UI: always render the parse as removable chips — 3 bed • house • Didsbury • ≤£400k • garden. A wrong parse becomes a minor annoyance instead of a failed search. Cheapest resilience you can buy.
    An eval harness: 500+ golden queries with expected parses, run in CI, tracking per-tier coverage and fallback rates. "Bulletproof" requires measurement, and this harness also trains the confidence threshold.

2. Security: server-side, hardened — on-device LLMs are strictly worse here

Direct answer to your question: architect it server-side. A local LLM on the user's device makes every one of your concerns worse:

    The data lives server-side regardless. You can't search a million-listing vector index on a phone. So a local LLM means shipping listings data to the device — you've expanded your exposure surface, not shrunk it.
    Client-side = zero control. The user owns the runtime: they can inspect the model, extract prompts trivially, inject anything, and you can't audit, rate-limit, or patch. Prompt injection defense is impossible when the attacker controls the environment.
    Quality and UX collapse: phone-grade quantized models are weak at structured extraction, and a multi-GB model download kills onboarding.

The correct security posture instead: treat the LLM as an untrusted, already-compromised component, and bound its blast radius to zero. Concretely:

    The LLM never touches the database. It emits schema-validated JSON filters; your code builds parameterized queries. A fully jailbroken parser LLM can produce... unusual search filters. That's the entire blast radius.
    System prompts are not a security boundary. Assume they leak. No secrets, keys, or internal logic in them — leakage becomes embarrassing, not catastrophic. Add a canary token to detect extraction attempts.
    Data minimization: the parser LLM sees only the query string — no listings data at all. The chat LLM sees retrieved listings, which are public marketing data agents want exposed. PII is stripped before any LLM call and hydrated server-side after the response.
    No tool access on any path that handles untrusted input, strict Pydantic output validation (malformed → fallback tier, never executed), read-only DB role on the search path, per-session token budgets.

The genuinely sensitive assets — user PII, auth tokens, commercial terms — never enter an LLM context under this design. Optional extra paranoia: self-host a small fine-tuned model for the parsing step so query text never leaves your infrastructure at all.
3. Adaptive ingestion: LLM maps once, then runs deterministic forever

The pattern that solves "agents shouldn't reformat anything":

upload (CSV / BLM / XML / JSON / XLSX / SFTP feed)
  → format detection + field sampling
  → mapping: known format? apply stored preset
             new source?  LLM proposes field mapping → agent approves ONCE → stored
  → all future syncs run deterministically (zero LLM cost)
  → validate → geocode (postcodes.io) → UPRN match → enrich (EPC, sold prices)
  → dedup → staging → agent review → publish → async embed + POI scoring

Three things that make this work in the UK specifically:

    BLM is the de-facto industry standard — the pipe-delimited Rightmove format that every agent CRM (Alto, Jupix, Reapit, Expert Agent, Street) already exports. Build a first-class BLM parser and most agents need literally zero reformatting.
    The LLM is used once per source, not per listing — schema mapping is a perfect LLM task: one-shot, human-approved, then cached as a deterministic config. Negligible cost, human in the loop, no runtime risk.
    UPRN is your dedup golden key — OS Open UPRN is free (OGL). Match listings to UPRN and you can dedup the same property across sources and cleanly join EPC + Land Registry sold history.

Your historical demo data fits perfectly: run it through the identical pipeline to validate mapping, validation, and dedup before any live agent feed exists.

Yes — strongly, with one important adaptation. This project is unusually well-suited to TDD, because of the architecture decisions we've already made. Let me be precise about where it applies and where classic TDD breaks down:
Where TDD fits perfectly (most of this codebase)

We've deliberately pushed the critical paths into deterministic, pure functions — the Tier-0 parser, field-mapping transforms, validation, dedup scoring, POI distance computation, cursor pagination, SQL builders. These are textbook TDD territory: crisp input/output contracts, no I/O, microsecond tests. The golden-query suite we built is the parser's specification — adding a failing golden query first, then extending the parser, is exactly red-green-refactor. For a system whose core promise is "bulletproof," tests-as-merge-gates isn't optional; it's the mechanism that makes the promise credible over hundreds of changes.
Where classic TDD breaks down — and what replaces it

LLM components. You can't red-green a prompt — outputs are non-deterministic, so exact-match assertions are flaky by design. The replacement is eval-driven development: golden datasets with property-based assertions rather than exact outputs. For the LLM parser: "output validates against ParsedQuery schema, location ∈ gazetteer, prices within sane bounds." For chat: "every number in the response appears in the computed data" (grounding check), "no PII tokens present," "schema-valid." Same discipline, different assertion style.

Service boundaries get contract tests — the AI service's OpenAPI schema validated in CI, plus consumer-driven contracts so the TypeScript API server and Python AI service can't drift apart silently.

The DB layer needs integration tests against real Postgres (testcontainers/docker in CI) — our current test_search.py only verifies SQL string shape, not that the hybrid query actually executes correctly against pgvector. That's a gap to close before production data.

Frontend/exploratory UX — TDD's weakest fit; component tests and the prototype-driven iteration we've been doing are more honest there.

So the working rule for the project: TDD for everything deterministic, eval-driven for everything probabilistic, contract tests for everything between services — with CI gates on the golden suites, per-tier routing metrics, and fallback rates (which also operationalises your three cost-saving claims into measurable regressions tests).

compound-type parser fix

Good news and embarrassing news. Writing this fix exposed a worse latent bug: \bdetached\b has always matched inside "semi-detached" (the hyphen creates a word boundary), so every "semi-detached" query was silently parsed as [semi-detached, detached] — returning detached houses mixed into semi searches. The golden suite would have caught this on its first run; I should have run it against real data sooner. The compound fix below kills both bugs with the same mechanism.

The two failure modes, one fix:

    Type pollution — "detached bungalow" emitted [detached, bungalow], so a bungalow search returned detached houses too. Fix: a compound pattern consumes the whole phrase as one span first, and negative lookahead/lookbehind guards stop the standalone patterns double-firing.
    Confidence suppression — if I'd only suppressed the standalone match, the "detached" token would go uncovered, dropping confidence below 0.85 and needlessly routing bungalow queries to the LLM tier. The compound span keeps coverage intact, so these stay Tier-0.

Also folded in adjacent UK compounds while the mechanism was hot: townhouse → terraced, duplex (apartment) → maisonette (with a lookbehind so "apartment" doesn't double-fire), penthouse → flat, and chalet/dormer bungalow variants.
