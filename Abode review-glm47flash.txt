1. Critical Bugs
1.1 Price Parser: False k/m Detection
File: ai-service/app/parser.py (lines 84–88)


k_or_m = q_lower[pm.start():pm.end()].lower()
if "k" in k_or_m or "m" in k_or_m:
    max_price = float(raw_val.replace("k", "").replace("K", "")) * 1000
The check if "k" in k_or_m or "m" in k_or_m matches the letter "m" inside words like "max", "min", "mansion", etc. For example, "max £300k" would incorrectly trigger the ×1000 multiplier on the already-correct value, and "up to £2m" would also match "m" in "max" if the query contained it. The k check is similarly fragile — it matches any "k" in any word in the match span.

Fix: Check if the multiplier suffix is a standalone token, not a substring:


suffix_match = re.search(r"[kKmM]\b$", k_or_m)
if suffix_match:
    multiplier = 1000 if suffix_match.group().lower() == "k" else 1_000_000
    max_price = float(raw_val) * multiplier
else:
    max_price = float(raw_val)

1.5 HashEmbedder Produces Degenerate Vectors
File: ai-service/app/llm.py (lines 49–58)


digest = hashlib.sha256(text.encode()).digest()  # 32 bytes
for i in range(self.dim):  # 768 dimensions
    chunk = digest[i % len(digest) : (i % len(digest)) + 4]
With a 32-byte digest and 768 dimensions, i % 32 cycles through only 32 unique 4-byte chunks. This means dimensions 0, 32, 64, ... all have the same value, dimensions 1, 33, 65, ... all have the same value, etc. The resulting vector has only 32 unique values repeated 24 times. This makes the "semantic similarity" comparison meaningless — nearly any two queries will have similar cosine similarity.

Fix: Use a proper hash-based approach, e.g., multiple independent hash functions:


for i in range(self.dim):
    h = hashlib.sha256(f"{i}:{text}".encode()).digest()
    val = int.from_bytes(h[:4], "big")
    result.append((val % 10000 - 5000) / 5000.0)
1.6 SQL Injection via String Interpolation
File: ai-service/app/repository.py (line 120)


vec_str = f"[{','.join(f'{v:.6f}' for v in embedding)}]"
sql = (
    f"SELECT ... WHERE {where_sql} "
    f"ORDER BY embedding <=> '{vec_str}'::vector "
    ...
)
The embedding vector is interpolated directly into the SQL string. While the values are floats (reducing injection risk), this is a bad practice and vulnerable to edge cases (e.g., if embedding contains nan, inf, or a non-numeric string). It also prevents query plan caching.

Fix: Use a parameterized query:


sql = (
    f"SELECT ... WHERE {where_sql} "
    f"ORDER BY embedding <=> ${limit_param_idx + 1}::vector "
    f"LIMIT ${limit_param_idx}"
)
params.append(vec_str)

1.9 _longest_common_substring Returns Wrong Position
File: ai-service/app/ingestion/dedup.py (lines 113–121)


def _longest_common_substring(a: str, b: str) -> str:
    m = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    longest = 0
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i - 1] == b[j - 1]:
                m[i][j] = m[i - 1][j - 1] + 1
                if m[i][j] > longest:
                    longest = m[i][j]
    return a[max(0, i - longest):i]  # BUG: i is the LAST loop value
The return statement uses i which is the value from the last iteration of the outer loop (i.e., len(a)), not the position where the longest common substring actually ends. This returns the wrong substring (or an empty string).

Fix:


def _longest_common_substring(a: str, b: str) -> str:
    if not a or not b:
        return ""
    m = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    longest = 0
    end_pos = 0
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i - 1] == b[j - 1]:
                m[i][j] = m[i - 1][j - 1] + 1
                if m[i][j] > longest:
                    longest = m[i][j]
                    end_pos = i
    return a[end_pos - longest:end_pos]

2. Security Concerns
2.1 Rate Limiter Bypass via X-Forwarded-For Spoofing
Files: ai-service/app/routers/poi.py (lines 54–59), api/src/routes/auth.ts (lines 81–88)

Both the Python and TypeScript rate limiters trust the X-Forwarded-For header to determine the client IP. Since the servers are not behind a trusted reverse proxy in the default configuration, any client can set this header to bypass rate limits:


X-Forwarded-For: 1.2.3.4
X-Forwarded-For: 5.6.7.8
Each request appears to come from a different IP, defeating the rate limiter entirely.

Fix: Use request.client.host (the actual TCP connection IP) as the primary source, and only use X-Forwarded-For when behind a verified reverse proxy. In Fastify, trustProxy: true is set (line 29 of app.ts), which means Fastify will use X-Forwarded-For — this is correct only if there's a trusted proxy in front. Add validation to ensure the proxy is trusted.

The get() method iterates over all cache entries (up to 10,000) to find the best semantic match. Even with bucket pre-filtering, this is O(n) per lookup.

3.3 Sequential Upserts
File: ai-service/app/ingestion/pipeline.py (lines 67–79)


async def persist_listings(listings, upsert_fn, batch_size=100):
    for i in range(0, len(listings), batch_size):
        batch = listings[i : i + batch_size]
        for listing in batch:
            await upsert_fn(listing)  # One at a time!
            count += 1
Despite the batch_size parameter, items are processed one at a time. For 10,000 listings, this means 10,000 sequential database round-trips.

Fix: Use asyncio.gather() for concurrent upserts or batch SQL:


import asyncio
async def persist_listings(listings, upsert_fn, batch_size=100):
    count = 0
    for i in range(0, len(listings), batch_size):
        batch = listings[i : i + batch_size]
        await asyncio.gather(*(upsert_fn(l) for l in batch))
        count += len(batch)
    return count
